# RAG 混合检索架构与赛事隔离机制

> 本文档**诚实标注**本系统的检索实现，可作为参赛文档中「技术创新点」的引用依据。

## 1. 一句话定位

本系统以赛事 ID 为检索边界，同时校验年份和文档版本。RAG 只检索保存的原文证据，结构化事实由 Agent 从赛事主表读取，两者不混为一类“官方引文”。默认不依赖外部服务；可选本地语义模型或远程 Chroma。

## 2. 为什么需要「赛事隔离」

普通的 RAG 把全部文档塞进同一个向量库，靠 top-k 相似度取片段。在**高校竞赛导航**场景下这会引出两个真实痛点：

1. **跨赛事污染**：用户问「蓝桥杯的报名截止时间」，若语料里「互联网+」的截止时间向量更近，就会把错误赛事的字段答出来。
2. **年份/版本混淆**：同一赛事不同届次规则不同，混库检索会返回旧届次证据。

本系统把每个 `competition_id` 作为检索边界：远程 Chroma 每个赛事一个 collection，并增加 metadata 过滤；默认本地检索直接读取该赛事证据。查询指定的年份或版本不匹配时，所有路径均返回空结果。该约束降低串赛事风险，但不能代替源数据质量检查。

## 3. 三层混合检索信号

| 层 | 机制 | 作用 | 权重 |
| --- | --- | --- | --- |
| ① 可选语义向量 | `all-MiniLM-L6-v2`（384 维，需另行准备本地模型）句向量余弦 | 对官方原文进行语义召回 | 启用时 0.8 |
| ② 中文词项检索 | 无模型时 jieba 搜索分词 + BM25Plus；启用语义时使用分词重叠度 | 默认离线证据排序，启用模型时参与混合排序 | 启用语义时 0.2 |
| ③ 结构化事实路由 | 报名截止、参赛对象等由 Agent 读取主表 | 事实回答另关联对应原文；不作为伪造的引用块 | 不计入 RAG 排序权重 |

默认路径按当前赛事的证据原文和字段检索标签建立 BM25Plus 索引。标签只用于召回，不写入返回的原文。查询包含少量明确的词项扩展，如“几个人”扩展为“团队、人数、队伍”；这不保证一般语义理解。零词项交集的片段不因 BM25Plus 平滑项而被召回，空语料直接返回空结果。分词和索引使用有界缓存，索引键包含原文及字段，修改原文后不会继续使用旧索引。

启用语义时排序 = `0.8 × 语义余弦 + 0.2 × 分词重叠度`，原文块向量按 `competition_id` 缓存到内存。赛事入库更新清理对应缓存；重新灌库清理全部缓存。

> **诚实标注**：默认路径（无远程 Chroma）下，向量检索在进程内对 DB 片段做余弦排序，**不依赖 Chroma 服务**——既绕开了受限环境下 Chroma 持久化的磁盘段错误，又拿到了真正的语义召回。Chroma 仅作为「接入外部大规模向量库」的可选增强，而非必需组件。

## 4. 可选语义与离线兜底

- 当 `all-MiniLM-L6-v2` 已离线预热到本地 HF 缓存时，**RAG 默认即为真实语义向量检索**，无需任何环境变量、无需联网。
- 环境变量开关（向后兼容）：
  - `RAG_USE_ST=0` → 强制关闭语义模型，使用本地 jieba + BM25Plus。`embedding_backend=light-hash-256` 是向量函数标签；实际检索路径由 `retrieval_backend=jieba+bm25plus` 表示，不能据前者宣称语义搜索。
  - `RAG_USE_ST=1` → 强制开启真实 embedding。
  - 不设 → **本地有模型即自动开启**，缺失模型时优雅降级到轻量向量 + 关键词，保证服务零外部依赖可启动。
- 加载模型时若检测到本地缓存，自动置 `HF_HUB_OFFLINE=1`，规避受限网络下连 huggingface.co 超时卡死。

## 5. 可解释与可追溯（引用门控）

每条召回片段都携带完整 `Citation`：来源字段、官方文档名、官方链接、获取日期、最后核验时间、可信等级。Agent 引用门控会在「证据不足 / 字段无对应证据」时**主动拒答或提示人工复核**，而非编造——这比「能编出答案的 AI」更可信，是第二个创新点。

引用还保留证据 ID、文档 ID、SHA-256 与已有定位信息。缺失元数据保持缺失，不从赛事摘要补造。远程召回须匹配当前版本及原始文本，再返回数据库中的原始 Citation；旧摘要块、旧版本或被修改的文本不作为引用。

## 6. 与 naive RAG 的对比（可用于答辩）

| 维度 | 朴素 RAG | 本系统 |
| --- | --- | --- |
| 跨赛事隔离 | 无，易串味 | 按 competition_id 硬隔离 |
| 词项与语义 | 依赖单一向量库 | 默认中文 BM25Plus，可选语义 + 分词重叠；事实另由结构化路由处理 |
| 外部依赖 | 常需向量库 + GPU | 零联网、零 Chroma 可跑 |
| 可追溯 | 片段难定位来源 | 每条带官方 Citation |
| 不确定处理 | 常硬答 | 门控拒答 / 提示复核 |

## 7. 部署建议

- **本地 / 比赛演示**：默认可用本地原文关键词检索。需语义检索时另行安装并预热模型，源码包不包含模型权重；模型加载失败时降级。
- **生产大规模语料**：设 `CHROMA_HOST` 接入远程 Chroma，每个赛事仍保持独立 collection，检索逻辑不变。
- **可选 LLM 润色**：设 `AGENT_LLM_API_KEY` 可在门控 + 检索结果之上做自然语言组织（默认空则用确定性模板，保证可复现）。

## 8. 当前检索对照

运行 `python evals/run_retrieval_comparison.py`，结果见 [retrieval_comparison.json](../evals/retrieval_comparison.json)。在两项赛事的 20 条开发者编写、按目标证据字段标注的问题中，旧字符重叠排序 Top-1 为 18/20、Recall@3 为 19/20；新路径分别为 19/20、20/20。该测试只比较证据排序，不代表整套 Agent 准确率，也不是独立留出集或真实用户研究。BM25 机制来自开源组件，项目实现的赛事隔离、引用还原和门控属于接入层。
